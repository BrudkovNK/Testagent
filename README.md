# Browser Agent — автономный AI-агент для управления браузером

Универсальный агент, который получает задачу текстом и сам, шаг за шагом,
доводит её до конца в реальном браузере: сам решает, куда перейти, что
нажать, что ввести, как понять, что действие сработало, и когда остановиться
и спросить пользователя. Никакой логики под конкретные сайты (почта, доставка
еды, hh.ru) в коде нет — это сознательное требование задания, и оно
выдержано по всему проекту.

## Как это выглядит

```
python -m src.cli "Прочитай последние 10 писем в Яндекс.Почте и удали спам"
```

Открывается видимый Chromium. Агент печатает в терминал каждый свой шаг
(рассуждение → действие → результат) и, если нужно, задаёт вопросы или просит
подтверждение прямо в терминале.

### Как агент "видит" страницу — без хардкода селекторов

Требование задания прямо запрещает захардкоженные CSS-селекторы вроде
`a[data-qa='vacancy']`. Решение: `dom_extractor.js` при каждом шаге сканирует
DOM живой страницы и строит **пронумерованный** список интерактивных
элементов (`[0] <button> role=button "Купить"`, `[1] <input> role=textbox
placeholder="Поиск"`, ...). Сами DOM-узлы кладутся в
`window.__agentElements[i]` — единственный контракт между моделью и
браузером — это **целое число**, а не строка-селектор. Модель никогда не
видит и не пишет ни одного CSS/XPath выражения; она может рассуждать только
в терминах "элемент №N выглядит как кнопка добавления в корзину". Это делает
подход одинаково рабочим на любом сайте, а не только на трёх примерах из
задания.

### Управление контекстом / токенами

Три независимых уровня сжатия, как и требуется в задании:

1. **DOM → компакт**: в модель никогда не попадает HTML. Вместо этого —
   короткий список элементов (роль, обрезанный accessible name, атрибуты) +
   опционально аннотированный "set-of-marks" скриншот (номера элементов
   нарисованы прямо на картинке, `dom_extractor.js::__agentMark`) — картинка
   стоит фиксированное число токенов независимо от сложности страницы, что
   намного эффективнее текстового дампа для визуально насыщенных интерфейсов.
2. **Один шаг → лимиты**: `MAX_ELEMENTS_PER_STATE` элементов на шаг,
   `MAX_TEXT_FIELD_CHARS` на одно текстовое поле, с явной пометкой "показано
   X из Y найденных" — модель знает, что список неполный, и может
   попросить `scroll`.
3. **История диалога → скользящее окно + сжатие** (`memory.py`): в
   "сыром" виде хранятся только последние `MAX_HISTORY_STEPS` шагов
   (нужны полные скриншоты/списки для точных действий), всё, что старше,
   схлопывается в однострочные записи progress-лога ("клик #7 'Купить' →
   товар добавлен"). Так задача из 30-40 шагов не взрывает контекст.

### Sub-agent architecture (продвинутый паттерн)

- **Planner** (`subagents.py`) — отдельный вызов LLM в начале эпизода,
  получает только текст задачи и строит 3-6 абстрактных подцелей
  ("перейти в сервис", "найти релевантный раздел", "оценить кандидатов по
  критериям", ...) — **без** знания конкретного сайта. План кладётся в
  системный промпт как ориентир, а не жёсткий сценарий: исполнитель волен
  от него отклоняться.
- **Executor** (`agent.py`) — основной цикл, который реально жмёт кнопки.
- **StagnationDetector** (`subagents.py`) — алгоритмический (не LLM)
  верификатор: хэширует `(url, список_элементов)` до/после действия; если
  несколько шагов подряд состояние не меняется — это почти наверняка
  означает, что предыдущее действие не сработало. Детектор не чинит это сам,
  а инжектирует явное предупреждение в контекст модели, вынуждая её
  проанализировать ситуацию заново, а не повторять то же самое действие
  вслепую. Это и есть требуемая "обработка ошибок — агент адаптируется".

### Security layer (второй продвинутый паттерн)

Деструктивные действия (оплата, безвозвратное удаление, финальная отправка
заявки/отклика/сообщения) перехватываются **дважды**, чтобы не полагаться
только на добросовестность модели:

1. Модель обязана (по системному промпту) сама вызвать `request_confirmation`
   перед таким шагом.
2. Дополнительно `security.py::element_looks_destructive` проверяет текст/роль
   элемента прямо перед выполнением `click` по ключевым словам-паттернам
   ("оплат", "удал", "отправ.*отклик", "delete", "pay", "confirm", ...) —
   если совпадение есть, а модель подтверждения не запросила, **выполнение
   всё равно останавливается** и подтверждение запрашивается принудительно.

Подтверждение выводится в терминал (`y/N`), и отказ пользователя явно
возвращается модели как результат инструмента — агент обязан не повторять
отклонённое действие.

### Что выбрано и почему

| Выбор | Обоснование |
|---|---|
| **Playwright** (не Selenium/Puppeteer) | Нативный Python API, persistent context "из коробки" (`launch_persistent_context`), надёжные авто-ожидания, официальный образ для Docker |
| **Claude (Anthropic tool use)** как основной провайдер, OpenAI — опционально | Tool use у Claude даёт чистый структурированный контракт действий; `llm_client.py` абстрагирует провайдера, чтобы это был вопрос конфигурации, а не архитектуры |
| **Индекс элемента вместо селектора** | Единственный способ гарантированно исключить хардкод и одновременно дать модели стабильную, компактную адресацию |
| **Set-of-marks скриншот + текстовый список** | Баланс точности (модель "видит" реальный layout, что критично для похожих элементов вроде вкладок/карточек товаров) и токен-экономии |
| **Persistent profile (`user_data_dir`)** | Требование "агент продолжает работу, если пользователь уже вошёл вручную" — сессии куки переживают перезапуск агента |

## Если нет платного ключа Anthropic

Провайдер LLM — вопрос конфигурации (`LLM_PROVIDER` в `.env`), а не кода:
`llm_client.py` абстрагирует Claude/OpenAI/Gemini за одним интерфейсом,
остальной проект (агент, инструменты, память) от выбора провайдера не зависит.

Два реальных способа не платить:

| Вариант | Что сделать | Качество для этой задачи |
|---|---|---|
| **Gemini (рекомендуется)** | `LLM_PROVIDER=gemini`, бесплатный ключ без карты на [aistudio.google.com/apikey](https://aistudio.google.com/apikey), вписать в `GEMINI_API_KEY` | Полноценная модель с tool calling и vision, есть дневной бесплатный лимит запросов — реально работающий вариант "в лоб" |
| **Локальный Ollama** | `ollama pull qwen2.5:7b` → `ollama serve`, в `.env`: `LLM_PROVIDER=openai`, `OPENAI_BASE_URL=http://localhost:11434/v1`, `OPENAI_API_KEY=ollama` (любая непустая строка), `OPENAI_MODEL=qwen2.5:7b` | Полностью бесплатно и локально (это ближе всего к духу "агента, живущего в Docker без внешних сервисов"), но небольшие модели заметно хуже держат длинную цепочку точных tool-calls, чем Claude/GPT-4o/Gemini — на сложных многошаговых задачах вероятны сбои, которые крупные модели не допускают |

Если есть ключ OpenAI (платный, но, возможно, уже есть) — `LLM_PROVIDER=openai`
с обычным `OPENAI_API_KEY` тоже работает без изменений в коде.

⚠️ **Ollama + Docker**: если сам агент запущен в контейнере (Вариант B ниже), а
Ollama — на хосте, то `http://localhost:11434/v1` из контейнера будет указывать
на сам контейнер, а не на хост, и соединение не установится. На Docker
Desktop (Mac/Windows) используйте `OPENAI_BASE_URL=http://host.docker.internal:11434/v1`.
На Linux — либо тот же `host.docker.internal` (если добавить в
`docker-compose.yml` `extra_hosts: ["host.docker.internal:host-gateway"]`),
либо IP хоста в докер-сети напрямую. Для нативного запуска (Вариант A) эта
проблема не возникает — там `localhost` действительно означает хост.

## Запуск

### Вариант A — нативно (проще всего, браузер — обычное окно на хосте)

```bash
git clone <this> && cd browser-agent
cp .env.example .env   # впишите ключ провайдера (см. "Если нет платного ключа Anthropic" выше)
./run_native.sh "Прочитай последние 10 писем в Яндекс.Почте и удали спам"
```
(или просто `./run_native.sh` и ввести задачу интерактивно)

### Вариант B — Docker (как просили в задании: всё локально, поднимается контейнером)

Поскольку требование задания — **видимый** браузер, а у Docker-контейнера
по умолчанию нет экрана, внутри образа поднимается виртуальный дисплей
(Xvfb) + VNC + noVNC, так что браузер остаётся буквально "видимым" — через
обычную вкладку в браузере на хосте.

```bash
cp .env.example .env   # впишите ключ провайдера (см. "Если нет платного ключа Anthropic" выше)
docker compose up -d --build
```

Дальше:
- **Смотреть на браузер**: открыть `http://localhost:7900/vnc.html` (Connect без пароля) — увидите тот же Chromium, что и в нативном режиме.
- **Отправить задачу / управлять через командную строку**:
  ```bash
  docker compose exec agent python -m src.cli "Найди 3 подходящие вакансии AI-инженера на hh.ru и откликнись"
  ```
  Терминал `docker compose exec` — полноценный TTY, поэтому `ask_user` и
  подтверждения (`y/N`) работают точно так же, как в нативном режиме.
- Профиль браузера (сессии/куки) хранится в именованном volume
  `browser_profile` — переживает пересоздание контейнера.

## Структура проекта

```
browser-agent/
├── src/
│   ├── config.py             # вся конфигурация через .env
│   ├── dom_extractor.js      # инжектируемый JS: индексация элементов + set-of-marks
│   ├── browser_controller.py # Playwright-обёртка (state/actions по индексу)
│   ├── tools.py               # схема инструментов + человекочитаемое описание вызовов
│   ├── llm_client.py          # Claude / OpenAI tool calling за одним интерфейсом
│   ├── memory.py               # скользящее окно истории + сжатие в progress-лог
│   ├── security.py             # эвристика деструктивных действий + подтверждение
│   ├── subagents.py            # Planner + StagnationDetector
│   ├── agent.py                 # главный Executor-цикл
│   └── cli.py                    # точка входа
├── docker/entrypoint.sh          # Xvfb + x11vnc + noVNC
├── Dockerfile / docker-compose.yml
├── requirements.txt / .env.example / run_native.sh
└── examples/example_tasks.md      # три сценария из задания — как проверить
```

## Честно об ограничениях

- Код написан и синтаксически проверен (`py_compile`), но **не прогонялся
  end-to-end** против реальных сайтов: у среды, в которой я это собирал, нет
  сетевого доступа и Docker-демона, так что я не мог выполнить `pip install`,
  скачать браузер Chromium через Playwright, поднять контейнер и реально
  открыть mail.yandex.ru/hh.ru/сервис доставки. Первый прогон на вашей машине
  вполне может выявить мелкие шероховатости (тайминги ожидания, edge-cases
  в извлечении элементов на конкретных сайтах) — это нормально для
  агентного кода такого рода, и они легко правятся по логам.
- Set-of-marks оверлей и скриншоты — стандартный, проверенный в индустрии
  паттерн (используется в browser-use, WebVoyager и похожих системах), но
  под конкретные тяжёлые SPA (сложные модалки, shadow DOM, iframe) может
  потребоваться донастройка `dom_extractor.js` (например, добавление обхода
  `shadowRoot`/вложенных `iframe`, которых сейчас нет, — самое вероятное
  первое улучшение при реальном тестировании).
- Security-эвристика — намеренно широкая по ключевым словам, а не по
  семантике; это может изредка просить лишнее подтверждение (ложное
  срабатывание безопаснее, чем пропуск реального деструктивного действия).
